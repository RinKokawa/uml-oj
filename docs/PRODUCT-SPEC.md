# UML OJ 产品与 MVP 规格

## 1. 产品定义

UML OJ 是一个通过测试用例验证 UML 建模正确性的在线评测系统。

它不是单纯的 UML 绘图工具，也不是只依赖 AI 主观打分的批改工具。用户根据业务需求建立模型，提交后由 Test Runner 执行题目提供的测试用例，系统给出整体判定和逐项结果。

## 2. 目标用户与使用场景

第一阶段优先服务于个人学习者，包括软件工程学习者、软件设计与架构考试复习者，以及希望练习面向对象分析与设计的开发者。

典型流程：

1. 选择一道中文建模题。
2. 阅读业务背景、需求和提交要求。
3. 选择作答方式：可视化绘图或源码编辑。
4. 完成 UML 类图。
5. 提交模型。
6. 系统解析输入并生成统一 UML IR。
7. Test Runner 执行该题的测试用例。
8. 查看 Accepted / Wrong Answer / 部分通过等结果及失败详情。
9. 修改模型并再次提交。

## 3. 核心产品原则

### 3.1 测试要求，而非比对唯一答案

题目应通过测试用例描述必须满足的建模要求。不得简单要求用户模型与某张参考图完全一致。

只要不同建模方案都满足题目明确要求，就应允许通过。题目作者需要明确哪些设计选择是强制要求，哪些只是建议或示例。

### 3.2 两种作答方式，共用评测内核

- 可视化建模：使用结构化节点、属性面板和关系连线创建模型。
- 源码建模：第一阶段优先支持 PlantUML。

两种输入都必须转换为统一 UML IR。画布 JSON 和 PlantUML 源码不是评测标准本身。

### 3.3 结果可解释、可复现

相同题目版本、相同测试集和相同提交模型，应得到相同的确定性测试结果。每个失败测试应说明失败条件，并尽可能定位到相关类、属性或关系。

### 3.4 AI 的边界

AI 可用于解释失败原因、辅助题目作者编写测试、或对确实无法形式化的开放式设计提供辅助意见。AI 结果必须与确定性测试结果区分显示，不得悄悄混入客观分数。

## 4. MVP 范围

### 必须实现

- 题目列表、题目详情与中文需求描述
- UML 类图可视化编辑
- PlantUML 源码编辑与预览
- UML IR 规范及输入适配器
- 类、属性、关联、继承、聚合、组合、依赖、多重性等基础元素
- 测试用例定义格式
- 确定性 Test Runner
- 提交记录与逐项测试报告

### 暂不实现

- 图片上传、OCR 和自由手绘识别
- 多人实时协作
- 排行榜、比赛和社交系统
- 全部 UML 图类型
- 依赖大模型才能完成的自动判分
- 复杂用户组织、班级和课程管理

## 5. 评测结果

建议至少支持以下状态：

- **Accepted**：所有必需测试通过。
- **Wrong Answer**：模型可解析，但一个或多个必需测试失败。
- **Compilation Error**：源码或输入无法解析为 UML IR。
- **Invalid Model**：输入可解析，但模型违反基础结构规则。
- **部分通过**：可作为展示分数或测试进度的状态；最终判定仍由必需测试是否全部通过决定。

不要把“部分通过”与 Accepted 混淆。

## 6. 第一阶段验收标准

1. 用户可以创建包含类、属性和关系的类图。
2. 用户可以通过 PlantUML 描述同一类图范围内的模型。
3. 两种输入均能转换为统一 UML IR。
4. 至少一题拥有多个独立测试用例。
5. 正确模型能够通过全部必需测试。
6. 修改某个关系类型或多重性后，对应测试能够失败。
7. 测试报告能指出失败测试及其检查条件。
8. 对同一提交重复运行，确定性测试结果一致。

## 7. 尚待决策

- UML IR 的正式 schema 与版本策略
- PlantUML 支持范围及解析实现
- 可视化画布组件与模型同步策略
- 测试 DSL 的语法、类型系统和安全限制
- 多重性方向的统一定义
- OCL 或轻量约束 DSL 的支持范围
- 题目版本、测试集版本与历史提交的关联方式
